# Terraform Repository Structure — Universal Template (Scale-Grade)

This template scales **down** (solo/small) and **up** (multi-account enterprise). Pick the tier that fits, then grow.

---

## The Core Principle: Two Layers

Every good large-scale Terraform setup separates two things:

1. **Modules** — _reusable, parameterized building blocks._ No hardcoded values, no environment specifics. "How to build a VPC." Versioned like software.
2. **Live / Environments (root configs)** — _thin compositions that call modules with real values._ "Build _this_ VPC in prod us-east-1." Each has its own **state**.

> **Golden rule:** Modules contain _no_ hardcoded environment data. Root configs contain _no_ resource logic — they only wire modules together with inputs.

State is partitioned by **blast radius**: a separate state file per (environment × region × component) so one mistake can't take down everything.

---

## TIER 1 — Minimal (solo / small project / learning)

```
my-infra/
├── main.tf                  # resources / module calls
├── variables.tf             # input variables
├── outputs.tf               # outputs
├── providers.tf             # provider config
├── versions.tf              # required_version + required_providers + backend
├── terraform.tfvars         # variable values (gitignore if it holds secrets)
├── .terraform.lock.hcl      # provider lock — COMMIT THIS
├── .gitignore
└── README.md
```

`.gitignore` essentials:

```gitignore
.terraform/
*.tfstate
*.tfstate.*
*.tfvars          # if they contain secrets; otherwise commit non-secret ones
crash.log
override.tf
```

## TIER 2 — Standard (single account, multiple environments, module library)

This is the **most common professional layout** and what you should default to.

```
infrastructure/
│
├── modules/                          # ── LAYER 1: reusable building blocks ──
│   ├── vpc/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   ├── outputs.tf
│   │   ├── versions.tf               # required_providers, NO backend in modules
│   │   ├── README.md                 # generated by terraform-docs
│   │   └── examples/
│   │       └── basic/
│   │           └── main.tf           # runnable usage example
│   ├── ecs-service/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   ├── outputs.tf
│   │   └── versions.tf
│   ├── rds/
│   │   └── ...
│   ├── s3-bucket/
│   │   └── ...
│   └── iam-role/
│       └── ...
│
├── environments/                     # ── LAYER 2: root configs (one state each) ──
│   ├── dev/
│   │   ├── main.tf                   # calls modules with dev values
│   │   ├── variables.tf
│   │   ├── outputs.tf
│   │   ├── providers.tf
│   │   ├── backend.tf                # remote state config for dev
│   │   ├── terraform.tfvars          # dev-specific values
│   │   └── .terraform.lock.hcl
│   ├── staging/
│   │   └── ...                       # same shape, staging values + own state
│   └── prod/
│       └── ...                       # same shape, prod values + own state
│
├── global/                           # account-wide resources (one state)
│   ├── iam/                          # IAM users/roles/policies
│   ├── route53/                      # DNS zones
│   └── s3-tfstate-backend/           # the bucket/lock that stores everyone's state
│
├── .github/
│   └── workflows/
│       ├── terraform-plan.yml        # plan on PR
│       └── terraform-apply.yml       # apply on merge (with approval gate)
│
├── .tflint.hcl
├── .terraform-docs.yml
├── .pre-commit-config.yaml           # fmt/validate/tflint/tfsec on commit
├── .gitignore
├── Makefile                          # make plan ENV=dev, make apply ENV=prod
└── README.md
```

**Why one folder per environment (not workspaces):** separate directories give each env its **own state file, own backend, own variable values, and physical isolation** — a `terraform destroy` in `dev/` literally cannot touch prod state. Most large orgs prefer this over CLI workspaces for exactly this blast-radius reason.

## TIER 3 — Enterprise (multi-account, multi-region, component-split state)

At scale you split further: by **account** (often per environment in AWS Organizations), then **region**, then **component**. Each leaf is an independent state.

```
│
├── modules/                          # the versioned module library (Layer 1)
│   ├── networking/
│   │   ├── vpc/
│   │   ├── transit-gateway/

│   │   └── asg/

│       ├── cloudwatch-alarms/

├── live/                             # Layer 2, sliced by account → region → component
│   │
│   ├── mgmt-account/                 # AWS Organizations / SSO / billing
│   │   └── global/
│   │       ├── organizations/
│   │       └── sso/
│   │
│   ├── shared-services-account/

│   │   │   ├── data/                 # ← own state (RDS, etc.)
│   │   │   └── apps/                 # ← own state (services on the cluster)
│   │   └── eu-west-1/
│   │       └── ... (same component split)

│   │
│   └── prod-account/

│           └── ...

│   ├── plan.yml
│   ├── apply.yml
│   └── drift-detection.yml           # scheduled plan to catch drift
│
├── .tflint.hcl
├── .terraform-docs.yml
├── .pre-commit-config.yaml
├── .checkov.yaml                     # or .tfsec/ config
├── infracost.yml                     # cost estimation in CI
├── CODEOWNERS                        # who must approve which paths
├── .gitignore
└── README.md
```

**State layout that matches this tree** (in the S3 backend):

```
s3://acme-tfstate/
├── dev/us-east-1/networking/terraform.tfstate
├── dev/us-east-1/eks/terraform.tfstate
├── prod/us-east-1/networking/terraform.tfstate
├── prod/us-east-1/eks/terraform.tfstate
└── ...
```

The `backend.tf` `key` in each leaf mirrors its path: `key = "prod/us-east-1/eks/terraform.tfstate"`.

## Standard Module-Internal Structure

Every module — small or large — should look the same so anyone can navigate it:

```
modules/vpc/
├── main.tf            # the actual resources
├── variables.tf       # all input variables (with descriptions, types, validation)
├── outputs.tf         # everything callers might need downstream
├── versions.tf        # terraform{} required_version + required_providers (NO backend!)
├── locals.tf          # (optional) computed locals if main.tf gets busy
├── data.tf            # (optional) data sources
├── README.md          # auto-generated by terraform-docs from the above
└── examples/
    ├── basic/
    │   └── main.tf
    └── complete/
        └── main.tf
```

**File-naming convention (universal):**
| File | Contains |
|---|---|
| `main.tf` | Primary resources / module calls |
| `variables.tf` | Input variable declarations |
| `outputs.tf` | Output declarations |
| `versions.tf` | `required_version`, `required_providers` |
| `providers.tf` | Provider configuration (root configs only) |
| `backend.tf` | Remote state config (root configs only — **never in modules**) |
| `locals.tf` | Local values |
| `data.tf` | Data sources |
| `terraform.tfvars` | Variable values (root configs only) |

> **Critical rule:** Modules **never** declare a `backend` and rarely a `provider` config — they _inherit_ the provider from the root config that calls them. Only root/live configs own `backend.tf`, `providers.tf`, and `terraform.tfvars`.

## Polyrepo Variation (very common at large orgs)

Instead of one monorepo, split into separate repos:

```
terraform-modules-vpc/          # one repo per module, independently versioned & tagged
terraform-modules-eks/             (consumed via git tags: source = "git::...?ref=v1.4.0")
terraform-modules-rds/
│
terraform-live-dev/             # one repo per environment/account
terraform-live-prod/
│
terraform-policies/             # shared governance
```

**Trade-off:** polyrepo gives clean per-module versioning and access control (great for many teams) but more overhead (cross-repo changes, version bumping). Monorepo is simpler to refactor atomically but harder to scope permissions. Many orgs run a hybrid: monorepo for `live/`, polyrepo (or a private registry) for `modules/`.

## Terragrunt Variation (DRY environment configs)

Terragrunt (by Gruntwork) exists to kill repetition in the `live/` layer. Same module library, but environments become tiny `terragrunt.hcl` files:

```
live/
├── terragrunt.hcl                    # root: remote_state, provider generation (DRY once)
├── _envcommon/                       # shared component config across envs
│   ├── networking.hcl
│   └── eks.hcl
├── dev/
│   ├── env.hcl                       # dev-wide vars (account_id, region)
│   └── us-east-1/
│       ├── networking/
│       │   └── terragrunt.hcl        # just: source + inputs (3-10 lines)
│       └── eks/
│           └── terragrunt.hcl
└── prod/
    ├── env.hcl
    └── us-east-1/
        ├── networking/
        │   └── terragrunt.hcl
        └── eks/
            └── terragrunt.hcl
```

A leaf `terragrunt.hcl` is tiny:

```hcl
include "root" { path = find_in_parent_folders() }
terraform { source = "git::git@github.com:acme/terraform-modules-vpc.git//.?ref=v2.1.0" }
inputs = {
  cidr     = "10.10.0.0/16"
  az_count = 3
}
```

Backend config, provider blocks, and state keys are generated automatically — no copy-paste across 50 environments. Know this pattern even if you don't adopt it; it comes up constantly in interviews.

## HCP Terraform / Terraform Cloud Variation

If using HCP Terraform, the _file_ structure is similar but state/runs move to the platform: you organize via **Projects → Workspaces** (often one workspace per environment×component), connect each workspace to a VCS path, and the backend becomes:

```hcl
terraform {
  cloud {
    organization = "acme"
    workspaces { tags = ["aws", "prod", "networking"] }
  }
}
```

## Naming & Tagging Conventions (the unwritten standard)

**Resource names in HCL** — use `this` for the single primary resource in a module, descriptive names otherwise:

```hcl
resource "aws_vpc" "this" { ... }            # one VPC per module → "this"
resource "aws_subnet" "public" { ... }       # multiple kinds → descriptive
resource "aws_subnet" "private" { ... }
```

**Real resource names** — consistent prefix pattern via locals:

```hcl
locals {
  name_prefix = "${var.project}-${var.environment}"   # acme-prod
}
# → acme-prod-vpc, acme-prod-eks, acme-prod-rds
```

**Mandatory tags** (enforced by policy-as-code):

```hcl
provider "aws" {
  default_tags {
    tags = {
      Project     = var.project
      Environment = var.environment
      Owner       = var.owner
      ManagedBy   = "terraform"
      CostCenter  = var.cost_center
    }
  }
}
```

## How the Layers Talk to Each Other

Components in separate states share data via:

1. **`terraform_remote_state` data source** — reads another state's outputs directly (simple, but couples states).
2. **SSM Parameter Store / outputs lookup** (preferred at scale) — networking writes `vpc_id` to SSM, eks reads it. Looser coupling.

```hcl
# eks/ reads the vpc_id that networking/ produced
data "aws_ssm_parameter" "vpc_id" {
  name = "/acme/${var.environment}/networking/vpc_id"
}
```

## Decision Guide: Which Tier?

| Situation                                               | Use                                    |
| ------------------------------------------------------- | -------------------------------------- |
| Learning, one project, one env                          | **Tier 1**                             |
| One AWS account, dev/staging/prod, a few components     | **Tier 2**                             |
| Multiple accounts, regions, many teams/components       | **Tier 3**                             |
| Tons of near-identical environments, sick of copy-paste | **Tier 3 + Terragrunt**                |
| Want managed runs, RBAC, policy, private registry       | **Tier 3 + HCP Terraform**             |
| Many teams needing isolated module ownership            | **Polyrepo + private module registry** |

## Interview Talking Points About Structure

When asked "how do you structure Terraform at scale," hit these:

- **Two layers:** versioned modules vs thin live/root configs.
- **State partitioning by blast radius:** per env × region × component, never one giant state.
- **Modules carry no environment data, no backend, no provider config.**
- **Directory-per-environment over workspaces** for physical isolation.
- **Component-split state** with cross-state data via remote_state or SSM.
- **Guardrails:** policy-as-code (Sentinel/OPA), CODEOWNERS, plan-on-PR/apply-on-merge, drift detection, cost checks.
- **Versioned modules** (git tags / private registry) so teams upgrade deliberately.

Being able to _justify_ this structure (why split state? why not workspaces? why no backend in modules?) is exactly the senior/staff signal interviewers listen for.
